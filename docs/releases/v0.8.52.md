# 0.8.52 — drop the unused `aliquot.notes` column (manual spec 7 → 8 step)

Spec 8 removes `aliquot.notes`. An aliquot never had a note of its own worth
reading: it borrows its stock's note, which `tm aliquot list` (`*notes`) and
`tm aliquot show` (`* notes`, plus the `* inherited from stock <id>` line)
already show since 0.8.50. The tool no longer reads or writes the column, new
ledgers never create it, and this release is the last implementation step of
the notes epic.

**This release drops a column, so read *Before upgrading* before you open an
older ledger with it.**

## Before upgrading

1. **Back up the ledger directory** (a copy of the Dolt database directory).
   The Dolt history is not a substitute: this step drops the column, and a
   backup is what makes the text recoverable if you decide you need it.

2. **Export any non-empty aliquot notes.** The `dolt` dump works at any time
   (it reads the column directly); the `tm` command needs a **spec-7 tool**
   (0.8.48–0.8.51 at the time of writing):

   ```sh
   dolt --data-dir LEDGER sql -r csv \
     -q "SELECT id, notes FROM aliquot WHERE notes IS NOT NULL AND TRIM(notes) <> ''" \
     > aliquot-notes.csv

   # with a spec-7 tool only (the whole record, in one file):
   uv run tm -l LEDGER aliquot list --all --json > aliquot-notes.json
   ```

   Check the dump before continuing. The spec-8 `tm aliquot show` cannot
   reconstruct a tube's own note: it shows the **stock's** note, which was
   always the visible one.

3. **Tag, then drop the column by hand.** `tm schema plan` does not diff
   core-table columns, so the drop is one manual `ALTER` (Dolt DDL is not
   transactional — the tag is your restore point):

   ```sh
   dolt --data-dir LEDGER tag pre-migrate-spec-7
   dolt --data-dir LEDGER sql -q "ALTER TABLE `aliquot` DROP COLUMN `notes`"
   ```

4. **Record the new spec counter with the 0.8.52 tool.** The plan compares the
   stored `spec_version` with the tool's (and a ledger last written by a spec-7
   tool also carries a different fingerprint), so it reports the meta as stale
   even though the Kinds already match:

   ```sh
   uv run tm -l LEDGER schema plan    # "schema is up to date" + "ledger_meta is stale"
   uv run tm -l LEDGER schema apply   # one commit: apply(schema): refresh ledger_meta
   ```

   No `--allow-destructive` is needed: there is no plan step, only the meta
   refresh. The commit writes `spec_version` 8, the fingerprint, the tool
   version and the `ledger.yaml` copy.

5. **Verify:** `tm status` shows spec 8, `SHOW COLUMNS FROM aliquot` has no
   `notes`, `tm check` is green and `tm schema plan` says up to date.

Rollback: restore the backup, or `dolt --data-dir LEDGER reset --hard
pre-migrate-spec-7` (that also discards the meta-refresh commit).

A ledger that skips the `ALTER` keeps a harmless unused column — the tool never
names it — but its counter stays at 7 until `tm schema apply` runs. Do not drop
the column while a spec-7 (or older) tool still reads that ledger.

## Old aliquot CSVs

An aliquot CSV exported **before** this release still carries a `notes` column.
`tm import` now rejects unknown columns, so drop that column before importing
an old file (`csvcut -C notes`, `cut`, or a text editor). A `tm export` run
after the upgrade no longer writes the column.

## What changed

- `src/tetramark/schema/model.py`: `SPEC_VERSION` 7 → 8; the spec history
  documents the column drop.
- `src/tetramark/schema/ddl.py`: `_create_aliquot` no longer emits `notes`, so a
  new ledger's `aliquot` table is `..., label, created_at` and
  `tests/data/golden/ddl_full.sql` matches it.
- `src/tetramark/core/objects.py`: `_ALIQUOT_COLUMNS` drops `notes` (so
  `tm aliquot edit --set notes=…` is the unknown-field usage error and the
  editable set is `quantity`, `unit`, `created_at`); the list filter allowlist
  drops `notes` (keep `stock_notes`); `list_aliquots`/`show_aliquot` records no
  longer carry `notes`. The dead `notes` branch of the edit-summary helper is
  gone. `stock_notes` keeps working everywhere.
- `src/tetramark/core/events.py`: the spec-6 event guard compares against the
  spec that introduced `aliquot_event.message` (`EVENT_MESSAGE_SPEC = 7`), not
  the moving `SPEC_VERSION`: a spec-7 ledger is no longer refused with the
  spec-6 message. A spec-6 ledger is still refused with the same text and the
  same 6 → 7 remedy.
- `src/tetramark/schema/diff.py`: `SchemaPlan.meta_stale` also compares the
  stored `ledger_meta.spec_version` with the tool's. A manual step changes no
  DDL that the planner can diff, so without this the `tm schema apply` in step 4
  would have nothing to do and the counter would never move to 8. The plan's
  JSON gains a `spec_version` block.
- `src/tetramark/ops/io_csv.py`: the aliquot CSV columns lose `notes` (import
  and export); the module docstring says an aliquot borrows the stock's note.
- `migration/spec/7-to-8/README.md`: the manual step, verbatim above. There is
  deliberately **no `migrate.py` and no safeguard code**: the planner cannot
  diff core columns, and the only decision (export the text you care about) is
  the operator's.
- `tests/test_aliquot_edit.py` (the removed field is now an unknown-field case),
  the `aliquot_show_*.json` goldens (the tube's own `notes` is gone, the
  stock's `stock_notes` stays), `tests/test_cli_objects.py`,
  `tests/test_aliquot_where_operators.py`, `tests/test_aliquot_stock_notes.py`,
  `tests/test_csv_io.py` (including a test that an old CSV with `notes` is
  refused), `tests/test_objects.py`, `tests/test_ddl.py`, and the spec-6/spec-7
  guard tests in `tests/test_migrate.py` plus the new spec-version-drift
  regression in `tests/test_schema_diff.py`.
- `docs/spec/01-concepts.md`, `docs/spec/06-cli.md`, `README.md`, the tetramark
  skill (`references/commands.md`, `references/recipes.md`): the aliquot's own
  `notes` is gone from the record, the list/show column sets, the edit prose and
  the `--where` allowlist; `stock_notes` stays everywhere.

## Upgrade

`spec_version` 7 → 8, through the manual step above. Nothing else changes: no
preset version moves, no stored value is rewritten (the dropped column is the
only data change), and `spec_version` 8 is the only schema change a spec-7
ledger has to record. An older tool still opens a ledger that skipped the
`ALTER`; the spec-8 tool never names the column either way.
