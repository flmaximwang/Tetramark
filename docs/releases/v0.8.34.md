# 0.8.34 — base 6 removes the slotless box capacities

`base` is **version 6**: the slotless `shelf`, `freezer` and `drawer` box kinds no longer declare a
`capacity` (12 / 6 / 1), so a shelf can hold a thirteenth box and a drawer a second. A ledger whose
stored copy still says 5 keeps the old write bound until it follows the manual
`migration/presets/base/5-to-6/` step. The existing `proteins` **version 4** preset does not change;
its `3-to-4` migration step now pins `base` 6 and refuses a base-5 closure, naming that step.

## What changed

The three numbers described one piece of furniture, not a kind, and they were **enforced on writes**:
the box layer reads the ledger's copy of `presets/base.yaml` and refused the (N+1)th tube or child box
with `box 'X' is full (capacity N aliquots + child boxes)`, while `tm box show --json` reported
`geometry.capacity: null` and `tm schema plan` treated the number as a no-op. The bound was invisible in
the data and only showed up as a refused write. Base 6 removes it: `shelf`, `freezer` and `drawer` are
slotless and unbounded like `incubator`. `mouse`'s `cage` keeps `capacity: 5` — a cage's occupant limit
is a rule of that kind, not of one cabinet.

| part | version |
|---|---|
| `base` | 5 → **6** |

Nothing in `src/` changes: the write check still reads `geometry.capacity`, it simply finds none. Every
other preset keeps its version, and the bundles keep theirs (`molbio` 3, `cellbio` 1, `angenet` 1).

## Upgrade

**There is no `migrate.py` for base 5 → 6.** Nothing in the database changes, so the step replaces the
ledger's stored copy of `presets/base.yaml` and lets `tm schema apply` write the counter, the
fingerprint and `tetramark_version` in one commit. The procedure is
[`migration/presets/base/5-to-6/README.md`](https://github.com/flmaximwang/Tetramark/blob/v0.8.34/migration/presets/base/5-to-6/README.md):

1. Back up the ledger directory (the preset copy is a file, not in Dolt history), then
   `cp migration/presets/base/5-to-6/base-6.yaml "$LEDGER/presets/base.yaml"`.
2. `tm schema plan` → `schema is up to date` plus `ledger_meta is stale`.
3. `tm schema apply` → one commit writing `preset_versions` (`base: 6`), the fingerprint,
   `tetramark_version` and the `ledger.yaml` copy. No DDL and no row moves.
4. `tm check` → no `FAIL`; a box the old bound refused is now recordable.

The steps are ordered and each installs its own frozen copy: a base-4 ledger runs
`migration/presets/base/4-to-5/` first, and that folder now installs a frozen `base-5.yaml` (version 5
**with** 12 / 6 / 1), so 4 → 5 → 6 stays reproducible after this bump. The base counters run after the
spec counters: `spec/5-to-6` (spec 6) then the scripted `spec/6-to-7` (spec 7) come first, and the
base step itself runs on a spec-7 ledger because `tm schema apply` writes the tool's current
`spec_version`; a spec-6 ledger runs `migration/spec/6-to-7/migrate.py --apply` first. A ledger with
`proteins` 3 runs `base/5-to-6` **before** `proteins/3-to-4`: the protein step targets a base-6
closure, refuses a base-5 ledger with a message naming `migration/presets/base/5-to-6/README.md`, and
writes nothing.

`migration/README.md` now records the maintenance rule this change needed: a change that relaxes or
tightens a **write check** needs a counter and a step folder even when no DDL and no stored value moves,
because two ledgers recording the same `preset_versions` must accept the same writes.

The settled specification is committed in
[`docs/spec/08-presets.md`](https://github.com/flmaximwang/Tetramark/blob/v0.8.34/docs/spec/08-presets.md)
(base catalogue entry, the v6 paragraph and the version/counter rule) and the operator
walk-through in
[`docs/guides/migrating-a-legacy-ledger.md`](https://github.com/flmaximwang/Tetramark/blob/v0.8.34/docs/guides/migrating-a-legacy-ledger.md)
(§0 Prepare: ordered frozen base 4 → 5 → 6, the plan/apply metadata refresh, the proteins prerequisite,
and `tm init` creating base 6 / proteins 4).

## Shipped skills

Both skills are stamped **0.8.34**. `skills/tetramark/SKILL.md` says a new ledger is spec 7 / `base` 6;
`skills/tetramark-schema/references/presets.md` lists `base` 6 and `proteins` 4, keeps the slotless box
rows unbounded, and documents the v6 capacity removal and the manual 5 → 6 step.

## Unchanged on purpose

- A base-5 ledger still opens, still records `base: 5`, and still refuses the (N+1)th tube or child box
  until it follows the step: the historical behaviour is preserved, not silently switched.
- Grid and rack geometry, slot capacity, box nesting and every rule are untouched.
- No historical release note, fixture ledger or user ledger is modified.
