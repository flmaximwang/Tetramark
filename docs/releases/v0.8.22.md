# 0.8.22 — `--where FIELD=` finds the empty fields

`tm entity list`, `tm stock list`, `tm box list`, `tm find --where` and the Python `where=`
facades now read an exact filter whose value is exactly the empty string as "the field is
empty": a row matches when the column is `NULL` or `''` for a text-like column, and when it is
`NULL` only for a non-text column. Before this release `--where purification_id=` compared
against `''` (so it never matched `NULL`, only a stored empty string) and ran the schema
coercion on `""`, so an empty `ref`, `enum`, `int` or `date` filter could raise or resolve an
alias instead of filtering.

The Python mapping form is fixed too: `where={"field": None}` used to become the literal text
`"None"` and match only a row storing that text. `None` now means the empty value, exactly
like `{"field": ""}` and the list form `["field="]`. Callers that relied on `None` matching
the literal text `"None"` must pass the string `"None"`.

## What changed

- **`field=` means "the field is empty".** It applies to `tm entity list`, `tm stock list`,
  `tm box list`, `tm find --where` and the Python `ledger.entities.ls` / `ledger.stocks.ls` /
  `ledger.boxes.ls` / `ledger.find` `where=` argument. A text-like kind field (`string`,
  `text`, `enum`, `sequence`, `ref`) and every core column except `created_at` match
  `(<expr> IS NULL OR <expr> = '')`; a non-text kind field (`int`, `decimal`, `bool`,
  `date`, `datetime`) and `created_at` match `<expr> IS NULL` only. There is no
  `CAST(... AS CHAR)` fallback: a stored `0` never looks empty.
- **An empty value is not coerced.** The schema coercion and the ref/alias resolver are
  skipped for it (an empty `ref`/`enum`/`int`/`date` filter raises no coercion error and does
  no alias lookup), and the filter adds no SQL parameter. The computed-field check still runs
  first: `computed_field=` exits 2 with `field 'x' is computed and cannot be set`.
- **The Python mapping accepts `None` and `""`.** `where={"field": None}`,
  `where={"field": ""}` and `where=["field="]` are the same filter. This is a bug fix: the
  mapping form used to stringify `None` to `"None"`, an exact match for that text.
- **Nothing else changed.** Whitespace-only values (`--where 'field=  '`) are still exact
  matches and do not select `NULL`; the literals `none` and `null` are still exact matches;
  `field~pattern` still never matches `NULL`, so `field~^$` does not select a `NULL` field;
  duplicate/mixed `=`/`~` filters still error as before; a kind that lacks the field still
  contributes no rows; and a non-empty `field=value` still coerces and compares with `= %s`.

## Upgrade

Nothing to migrate: `spec_version` stays 6 and the ledger format is unchanged. A ledger
written by any 0.8.x release opens unchanged. Only the meaning of the empty filter value and
of a `None` mapping value changed; both are described above.
