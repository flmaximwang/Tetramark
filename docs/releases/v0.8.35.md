# 0.8.35 — `--where` learns `!=`, `!~`, `<`, `<=`, `>` and `>=`

The shared `--where` filter backend grows six operators. `tm entity list`, `tm stock list`,
`tm box list`, `tm find --where` and the Python `where=` argument now understand
`'field!=value'`, `'field!~pattern'` and the ordered comparisons `'field<value'`, `'field<=value'`,
`'field>value'`, `'field>=value'`, next to the `'field=value'` and `'field~pattern'` they already
had. Nothing breaks: every filter that parses today parses to the same thing, and a filter that
does not parse is still a usage error (exit code 2) — its message now names the new operators.

## The operators

| Filter | Means |
|---|---|
| `'field=value'` | the column equals the value (unchanged) |
| `'field~pattern'` | the column's text form matches the pattern (unchanged) |
| `'field!=value'` | the column holds another value, or is `NULL` |
| `'field!~pattern'` | the column's text form does not match the pattern, or is `NULL` |
| `'field<value'`, `'field<=value'`, `'field>value'`, `'field>=value'` | the column compares to the value in the order of its type |

The operator is the one that follows the field name, so a value may contain `=`, `~`, `!`, `<` and
`>`. The field name is still an identifier, and whitespace before the name and between the name and
the operator is still skipped.

## The asymmetry between `NULL` and empty

`NULL` is not a value, so the negated operators do not mirror their positive ones exactly:

- `'field!=value'` is the complement of `'field=value'`: for every row exactly one of the two
  matches, and `'!='` also matches the `NULL` rows.
- `'field!~pattern'` is the complement of `'field~pattern'`: for every row exactly one of the two
  matches, and `'!~'` also matches the `NULL` rows.
- `'field!='` (an empty value) is the complement of `'field='` (the empty-field filter of 0.8.22):
  it matches the rows that **have** a value and excludes the `NULL` and the empty rows.

So `'field!=x'` finds the rows a plain `'field=x'` would miss (the `NULL` ones), while `'field!='`
is the way to ask for "this field is filled in".

## Ordered comparisons are typed

- `int` and `decimal` compare numerically; `date` and `datetime` compare chronologically.
- `string`, `text` and the core text columns compare in the database's collation order — the same
  order `'='` uses.
- The core `created_at` compares chronologically and its value must be an ISO date or datetime;
  anything else is a usage error.
- A `bool`, an `enum`, a `ref`, a `sequence` and a `computed` field have no order: an ordered
  comparison on one of them is a usage error (the enum declaration order is **not** used).
- A `NULL` never matches an ordered comparison.

`'field!='` is refused on a computed field exactly like `'field='` is, and `'field!~pattern'` is
accepted on a computed field exactly like `'field~pattern'` is.

## Per-field rules

`'='` may be used at most once per field and never together with another operator on the same field
(`field 'x' cannot be filtered with both '=' and '<op>' in --where`). Every other operator may be
repeated on one field and the repetitions are ANDed (`'created_at>=2024-01-01'` together with
`'created_at<2025-01-01'`). An empty pattern (`'name~'`) and an empty comparison value (`'count<'`) are
usage errors. The Python mapping form (`where={"name": "pUC19"}`) stays equality only.

`tm aliquot list --where` keeps its own exact-only parser and is unchanged; the shared operators
reach it in a follow-up.

## Upgrade

Nothing to migrate: no schema, preset, migration step or ledger format changed, and no existing
filter changes meaning. A filter that used to be rejected may now parse (a field named `x` with a
`!` in front of its operator), and the message of a rejected filter lists the new operators.
