# 0.8.41 — `tm stock list`: show the stocks an experiment can use

`tm stock list` now prints only the stocks whose derived status is `active` — at least one aliquot in
stock — the same "what is available" default `tm aliquot list` already has. `--all` restores the old
output, every `empty` and `depleted` stock included. The Python API follows: `ledger.stocks.ls()`
defaults to active stocks and `all_statuses=True` gives the full list. The table, its columns, the
`ORDER BY id` order and the CSV/JSON shapes are unchanged, and no ledger format moved
(`spec_version` stays 7); the only change is which rows the default listing returns.

## Behaviour change

A listing is the availability view, and a stock with no aliquot in stock is an audit row rather than
something a session can draw from. The default narrowed; everything else stayed put.

| Call | Before 0.8.41 | From 0.8.41 |
|---|---|---|
| `tm stock list` | every stock | only `active` stocks (at least one aliquot in stock) |
| `tm stock list --all` | — | every stock: `empty`, `active` and `depleted` |
| `ledger.stocks.ls()` | every stock | only `active` stocks (`all_statuses=False`) |
| `ledger.stocks.ls(all_statuses=True)` | — | every stock |

The three statuses are the derived values of spec §3: `active` when at least one aliquot is in stock
— "in stock" means the tube's status is `stored`; `depleted` when the stock has aliquots but none of
them is in stock (a tube that was never placed in a box is `pending`, so it is not in stock either);
`empty` when it has no aliquots at all.

`status` stays a derived view column and is **not** a `--where` field: `tm stock list --where
'status=active'` is the unknown-field usage error (exit 2), with or without `--all`. There is no
`--status` option for stocks and no `--empty`/`--depleted` alias — `--all` is the one scope flag.

## Highlights

- `tm stock list [KIND] [--all] [--where FILTER ...] [--where-any FILTER ...] [--json]`: only active
  stocks by default; `--all` adds the empty and depleted ones, with the same columns
  (`id kind entity_id entity_name aliquots_in_stock status`). `--all` is long-only, combines with
  `KIND`, `--where`, `--where-any`, `--json` and the global `--format table|csv`, and does not change
  the row order (by id within each kind), the short uuid ids, the `(none)` empty result or any exit
  code. The active scope is an extra SQL predicate, so it ANDs with the AND group and the OR group.
- `ledger.stocks.ls(kind=None, *, where=(), where_any=(), all_statuses=False)` mirrors the CLI
  exactly; the record shape is unchanged, `aliquots_in_stock` still an int.
- One batched read: the scope is an SQL predicate on the view's derived `status` column, ANDed into
  the existing per-kind statements of the single `query_many` round trip. No second query, no
  Python-side post-filter, so the listing keeps its cost.
- Left deliberately alone: `tm entity list` and `tm box list` have no availability notion and still
  print every row; `tm aliquot list` keeps its in-stock default from 0.7.2.
- Spec and skills updated in the same PR: spec §6.2 drops the false "the entity/stock/box lists have
  no availability notion" claim and §6.4 carries the exact Python signature;
  `references/commands.md` has the new synopses, `references/recipes.md` notes the default, and the
  migration guide's row-count recipe uses `--all`. Both `SKILL.md` files are re-stamped to 0.8.41.

## Upgrade

Nothing to migrate: no schema, DDL, preset, migration step or ledger format changed, and
`spec_version` stays 7. A script that counted or diffed the old full listing needs `--all` on the CLI
or `all_statuses=True` in Python; the old output is one flag away. `tm entity list` and `tm box list`
need no change.
