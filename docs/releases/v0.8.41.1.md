# 0.8.41.1 — `tm aliquot edit`: correct a tube's recorded values

`tm aliquot add` had no way back when a tube was recorded wrong. `tm aliquot edit` is that way back:
it corrects the **current** value of one tube and leaves the history alone.

```
tm aliquot edit ALQ --set field=value ... [-m MSG] [--json] [--dry-run]
```

`ALQ` is the full aliquot id (`<stock>.<seq>`) or one of its aliases, exactly as on `tm aliquot show`.
Four columns are editable: `quantity`, `unit`, `notes` and `created_at`. Everything else is refused with
the command that owns it — `label` through `tm aliquot label`, `status` through `tm aliquot status`,
the position (`box_id`/`slot`) through `tm aliquot move` — while `id`, `stock_id` and `seq` are
identity data and have no substitute command.

An edit corrects the present, it does not replay the past: the create/use/move events stay as they
were, and the remaining quantity is not recomputed from earlier consumption. A tube recorded with
500 ul, used down by 100 ul and then edited to `quantity=600` now holds 600 ul, while the use event
still records 100 ul.

Each successful edit appends one `edit` event whose amount, unit, position and status columns stay
empty, whose message holds the summary of the changed fields (with the optional `-m` reason appended
as `; reason: MSG`), and it is a single Dolt commit, so the exact column-by-column diff stays in the
ledger history. Validation applies to the **final** record after every `--set` and a failed edit
writes nothing: a quantity must be finite and greater than zero (zero points at `tm aliquot use`),
quantity and unit must end up both present or both empty, the unit is non-empty and at most 32
characters, `created_at` must be a timezone-free ISO datetime and cannot be cleared, and an edit with
no actual change is refused.

The Python API follows: `AliquotOps.edit()` takes the same `--set` pairs.

Nothing in the ledger format moved (`spec_version` stays 7); this release only adds the command, its
API and its documentation.
