# 0.8.47 — shared where operators and OR filters in `tm aliquot list`

`tm aliquot list` stops parsing `--where` on its own: it rides the shared
`tetramark.core.filters` backend that already serves the entity, stock and box
lists and `tm find`. The listing now takes the shared eight operators — `=`, `~`,
`!=`, `!~`, `<`, `<=`, `>`, `>=` — and the one `--where-any` OR group, in the CLI
and in the Python `where=` / `where_any=` arguments. It is CLI/API only: no
ledger step, no migration, `spec_version` untouched.

The compatibility rule is deliberately conservative: **raw equality is preserved,
typed values are for ordering only**. Every filter this command accepted before
still parses to the same SQL with the same parameter, and every result is
unchanged.

## The operators on the aliquot columns

The allowlist is unchanged: `id`, `stock_id`, `seq`, `box_id`, `slot`, `quantity`,
`unit`, `label`, `created_at` and `notes`. An aliquot has no kind row, so there are
no kind fields, and `status` stays the `--status` filter — in either group, with
any operator, the old `filter the status with --status, not --where` error is
returned.

- `=` and `!=` bind the raw text, exactly as the old exact-only parser did: a
  stored `seq`/`quantity` compares with the database's string-to-number coercion
  as before, so `seq=abc` is still accepted (and matches nothing) and
  `quantity=1.50` still matches a stored `1.5`.
- An empty value (`FIELD=`) keeps the aliquot rule: `NULL` or `''` on a text
  column, `NULL` only on `seq`, `quantity` and `created_at` (a stored `0` never
  looks empty). `FIELD!=` (the shared complement) matches the rows that have a
  value.
- `~` and `!~` match the column's text form, as on the other lists: `seq~^1` and
  `quantity~^2.` work, `NULL` never matches `~` and always matches `!~`.
- An ordered comparison is typed: `seq` is an integer, `quantity` a decimal,
  `created_at` an ISO date or datetime (a date means its midnight) and the other
  columns compare in the database's collation order. A non-numeric ordered value
  for `seq`/`quantity` is a usage error naming the option and the filter (`invalid
  --where 'seq>abc': the value 'abc' is not a number`), and the non-finite
  decimal spellings (`NaN`, `Infinity`) are refused the same way.

`--where` is ANDed; `--where-any` is one OR group ANDed with it, repeatable, and a
field may repeat there (`--where-any 'label~^cl' --where-any 'label~^ctl'`). The
OR condition is one parenthesised condition appended after the `--where`
conditions and before the in-stock scope, with its parameters in the same order,
so the alias statement stays aligned. The scope flags (`--all`,
`--not-in-stock`, `--status`, `--kind`, `--box`), the record shape, the
`stock_id`/numeric-`seq` ordering and the one batched rows+aliases read are
unchanged.

```sh
tm aliquot list --where 'quantity>=100' --where 'created_at>=2026-01-01' \
  --where-any 'label~^cl' --where-any 'label~^ctl'
```

Write filters in single quotes: `<`, `>` and `!` are special in the shell.

## Behaviour changes worth knowing

1. `a!=b`, `a<b`, `a>=b` and the rest used to be malformed/unknown-field errors
   (`a!`, `a<`); they are filters now. This is the intended extension.
2. A field name must be an identifier (the shared rule). A list filter's field is
   one by construction, so the only observable difference is that a mapping key
   such as `{"bad-name": "x"}` now says `'bad-name' is not a valid field name`
   instead of `unknown field(s)`. Both are usage errors (exit 2).
3. The parser skips whitespace before the field name and between the name and the
   operator only. The whole value after the operator is preserved verbatim,
   leading and trailing spaces included: `label=  ` still filters the two-space
   text and never trims.
4. `field 'x' appears twice in --where` is unchanged for a repeated `=`; any
   number of `!=`, `~`, `!~` and ordered filters on one field is new and ANDed.
5. An invalid pattern in either group is a usage error naming the option and the
   filter (`invalid regular expression in the --where filter 'label~['`), never a
   raw driver error. The happy path pays no extra query.

## What changed

- `src/tetramark/core/filters.py`: a backward-compatible `ordered_coerce`
  parameter on `build_conditions` and `build_any_condition` (a
  `Callable[[Filter], Any]`, consulted after the core `created_at` ISO rule and
  only for `<`, `<=`, `>` and `>=`); the module docstring records the aliquot
  list as the fifth user. Callers that omit it are byte-identical.
- `src/tetramark/core/objects.py`: `list_aliquots` parses both groups through
  `parse_filters`, refuses `status` in either group, checks fields with the
  shared `check_fields`, and builds the SQL with `build_conditions` /
  `build_any_condition`; a small aliquot adapter supplies the typed ordered
  values and keeps the aliquot empty-value SQL. `where_any=` is forwarded by
  `Aliquots.ls`. One `try/except LedgerError` around the batch turns an invalid
  pattern into a usage error.
- `src/tetramark/cli/aliquot.py`: the `--where` help names all eight operators,
  and `--where-any` is added with the shared OR-group wording.
- `docs/spec/06-cli.md`: the `tm aliquot list` synopsis and paragraph, §6.4 (the
  four lists and `tm find`), the valid-field and `--where-any` paragraphs.
- `README.md` and the `tetramark` skill (`SKILL.md`,
  `references/commands.md`, `references/recipes.md`).
- `tests/test_filters.py` (fast-lane adapter tests) and
  `tests/test_aliquot_where_operators.py` (real-Dolt CLI/API tests).

## Upgrade

Nothing to migrate: no schema, preset, migration step or ledger format changed,
and no existing filter changes meaning. `spec_version` stays 6.
