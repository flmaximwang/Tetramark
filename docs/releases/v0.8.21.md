# 0.8.21 — box kind fields at creation: `tm box add --set`

`tm box add KIND NAME` now fills the box kind's fields at creation with the same `--set
field=value` spelling `tm box edit` uses, so a box kind that declares a required field without a
default is creatable for the first time. The kind row is written with those values in the same
commit as the box, its slots and its view, and `--json` reports the coerced values as a new
`fields` object. The human line, `tm box show` and `tm box edit` are unchanged; the JSON gain is
additive, and nothing breaks or needs migrating.

## What changed

- **New: `tm box add … [--set field=value …]`.** Repeatable and long-only; `-s` keeps meaning
  `--slot`. Values are coerced and validated exactly as `tm box edit` coerces them: a required
  field without a default must be given, an unknown field lists the valid ones, and a computed
  field is refused.
- **The name and the placement stay arguments.** `--set name=…` exits 2 with
  `give the box name as the NAME argument`; `parent_box_id`/`parent_slot` are refused with
  `… is structural; place a new box with --in PARENT [--slot S]`; `id`, `kind` and `created_at`
  are refused with `… is structural and cannot be set`.
- **Notes take one spelling.** `--notes TEXT` and `--set notes=…` both fill the box notes; giving
  both exits 2 (`the box notes were given twice (--notes and --set notes=...)`) even when the
  values are equal.
- **`--json` gains `fields`.** It lists every explicitly given kind field (coerced) plus every
  non-computed field the schema gives a default to (that default); a kind with no fields reports
  `{}`. Every existing key and the human line `Created box …` are unchanged.
- **The Python API mirrors the CLI.** `ledger.boxes.add(..., values=...)` accepts a sequence of
  `field=value` strings or a mapping, like `ledger.entities.add` and `ledger.stocks.add`.
- **`tm box add-form` asks the kind's fields** after the name, in schema order (computed fields are
  never asked); a kind's own `name` field is not a second question because the NAME argument is
  canonical. The form still calls the same `add`.
- **A refusal writes nothing.** All validation happens inside the write, so a rejected add makes no
  commit and leaves `dolt_status` clean.

## Upgrade

Nothing to migrate: `spec_version` stays 6, the ledger format is unchanged and no preset changes.
A ledger written by any 0.8.x release opens unchanged. This is a CLI/API change only, and the new
`fields` key is additive.
