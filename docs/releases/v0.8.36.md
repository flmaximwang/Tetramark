# 0.8.36 — `--where-any`: one OR group across `--where` filters

Filters could only be ANDed, and OR existed only inside a single regex. This release adds one OR
group: the repeatable `--where-any FILTER` on `tm entity list`, `tm stock list`, `tm box list` and
`tm find`, and the matching `where_any=` keyword on `ledger.entities.ls`, `ledger.stocks.ls`,
`ledger.boxes.ls` and `ledger.find`. A row must satisfy every `--where` filter **and** at least one
`--where-any` alternative:

```console
$ tm stock list --where 'kind=plasmid_prep' --where-any 'resistance=kan' --where-any 'resistance=amp'
```

reads as `kind=plasmid_prep AND (resistance=kan OR resistance=amp)`. Without `--where-any` nothing
changes; there is exactly one OR group per invocation.

## Semantics

- The group takes the same syntax, the same eight operators, the same coercion, type rules and
  empty-value rules as `--where` — one parser, one SQL builder.
- One exception: the per-field repetition rules do not apply inside `--where-any`. Repeating a field
  is how an alternative is written (`--where-any 'resistance=kan' --where-any 'resistance=amp'`), and
  there is no cross-check between the two groups.
- Per kind, an alternative whose field the kind does not declare is dropped (it is false for that
  kind). A kind that was given `--where-any` but has no surviving alternative contributes no rows,
  exactly like a kind that lacks a `--where` field. `tm find` still searches the union of the
  entity/stock/box kinds.
- Errors name the group the filter came from: `invalid regular expression in the --where-any filter
  'name~['` and `unknown field(s) 'nope' in --where-any; valid fields: …`.
- The surviving alternatives become one `(cond OR cond …)` condition appended to the kind's AND
  conditions, with their parameters in order, in the same single `query_many` batch as before.

## `tm find` and the Python API

`tm find` applies `--where-any` to every hit after the search, rewrite hits included; rewrites never
rewrite a filter. With no `QUERY`, either group lists every match (`match` = `filter`), aliquots are
excluded whenever either group is given, and the no-input error now reads `the search query must not
be empty; pass a QUERY or at least one --where or --where-any filter`. A miss reads `no objects match
the --where filters` when only `--where` was given and `no objects match the --where/--where-any
filters` once `--where-any` is.

The Python API mirrors the CLI: `where_any=` on the four facades takes a list of strings with any
operator or a mapping (equality only, a `None`/`""` value meaning "is empty"), exactly like `where=`.

## Upgrade

Nothing to migrate: no schema, preset, migration step or ledger format changed, and no command that
worked changes meaning. `tm aliquot list --where` keeps its own exact-only parser and takes neither
the 0.8.35 operators nor `--where-any` in this release.
