# 0.8.30 — `tm` survives a foreign PYTHONPATH and says when its install drifts

An installed `tm` is only useful to an agent if it starts in the environment the agent has, not only
in a clean one. Two failures stood in the way. A `PYTHONPATH` entry pointing at another interpreter's
`site-packages` could win the import race and kill `tm` with an ImportError traceback from a
`pydantic_core` built for a different Python; and an editable install whose metadata lagged behind
its code answered `tm --version` with a version that was no longer true. Both are handled at the
entry point now. Additive: every real ledger command, schema, preset and output format is unchanged
and nothing needs migrating.

## What changed

- The `tm` console script is now `tetramark._entry:main`. Before importing the CLI it sanitizes
  `sys.path`: an entry is dropped only when it carries a `python3.<X>[t]` component whose *X* is not
  the running minor version **and** a `site-packages`/`dist-packages` component, and never when it is
  under `sys.prefix`, `sys.base_prefix` or the checkout's `src`. Dropped entries are named in
  exactly one stderr line: `tm: ignoring PYTHONPATH entries from another Python: <entries> (unset
  PYTHONPATH to silence this)`.
- If the CLI still cannot be imported, `tm` exits 2 with exactly one actionable stderr line instead
  of a traceback: it names the failing top-level module, the first `sys.path` entry that holds it
  and the fix (`unset PYTHONPATH or remove that entry`), or — with `PYTHONPATH` unset — says the
  installation is broken and to reinstall `tm`.
- `import tetramark` no longer imports the ledger machinery or its dependencies. `__version__` stays
  eager; `Ledger`, `open`, `init_ledger` and `adopt_ledger` are resolved lazily through PEP 562,
  with `__dir__` and `TYPE_CHECKING` imports. `__all__` is unchanged, and `from tetramark import
  Ledger, open, init_ledger, adopt_ledger, __version__` keeps working.
- `tm --version` keeps its single stdout line `tetramark <version>` and adds one stderr warning when
  installed metadata disagrees with the code: it names both versions, the editable checkout
  (`direct_url.json`), and the pinned command
  `uv tool install --reinstall "git+https://github.com/flmaximwang/Tetramark@v<version>"`. It reads
  only local metadata; no network call, no PyPI lookup.
- `docs/spec/06-cli.md`: the global-options `--version` row documents the warning. No schema, preset
  or ledger-format change.

## Upgrade

Nothing to migrate: `spec_version` stays 6, every command keeps its options, output and exit codes,
and an editable install that already matches its checkout prints exactly what it printed before —
one stdout line and no warning.
