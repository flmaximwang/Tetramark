# 0.8.51 — `tm entity note` and `tm box note`

0.8.49 added `tm stock note`; this release gives the other two note-bearing objects the same
command: `tm entity note` and `tm box note` take identical flags and behaviour, run through the
same implementation, and print their group's `edit` line. It is CLI-only: no schema change, no
migration, `spec_version` stays 7.

```sh
tm entity note pUC19                     # open the current note in $VISUAL/$EDITOR/vi
tm entity note pUC19 --append "sequence checked 2026-11-07"
tm box note FR-1 --append "door seals replaced"
tm box note FR-1 --clear
```

## The commands

- `tm entity note REF [TEXT] [--append] [--clear] [--json]` and
  `tm box note REF [TEXT] [--append] [--clear] [--json]` behave exactly like `tm stock note`
  (0.8.49): a bare REF opens the current note in `$VISUAL`, then `$EDITOR`, then `vi`, with a
  git-style scissors line under the value; an unchanged buffer prints exactly `no changes`, exits 0
  and writes nothing. `--append TEXT` adds the text as one more line (a single `"\n"` separator,
  omitted when the note is empty), a bare `--append` opens an **empty** buffer and appends its
  result, and `--clear` sets the notes to `NULL`. An empty result without `--clear` is a usage
  error (exit 2) pointing at `--clear`; `TEXT` without `--append` and `--append` with `--clear` are
  usage errors too.
- `TEXT` stays a **positional** argument (before or after `--append`) because typer 0.27.3 cannot
  express an option with an optional value; the documented invocations are unchanged.
- The human line matches the group's `edit` command: `Edited entity <kind> <id>` and
  `Edited box <name> (<kind>)`. `--json` (local or global) prints the loaded record and
  `--dry-run` prints the buffered `UPDATE` and writes nothing. Each call is one write session and
  one Dolt commit (`edit(entity): <kind> <id>`, `edit(box): <kind> <id>`; the note text stays out of
  the ASCII-only summary).
- `REF` resolves exactly like the group's `edit`: an entity by full id, exact alias or unique id
  prefix (an ambiguous prefix is a usage error); a box by its human name first, then id, alias or
  unique id prefix.

## What changed

- `src/tetramark/core/objects.py`: `read_note(ledger, object_type, ref)` — the current note for one
  entity/stock/box with the same resolution as the writer, in the same one round trip (`edit`'s
  resolution already reads the whole core row, so it never loads a stock's aliquots just to read
  one text field); the shared `_check_note_object`/`_resolve_note_target` helpers now serve both
  `read_note` and `note_object`; `EntityOps.note()` and `BoxOps.note()` facades join
  `StockOps.note()`.
- `src/tetramark/cli/notes.py` (new): the one implementation of a note command — flag validation,
  the editor wiring (`_note_editor` with the light `read_note` pre-read), the `no changes` rule,
  the group-specific human line and `emit_write`. `tm stock note` moved its body here, so the
  three commands in `cli/stock.py`, `cli/entity.py` and `cli/box.py` are thin wrappers with their
  own arguments and docstring; no note logic is duplicated.
- `docs/spec/06-cli.md`, `skills/tetramark/references/commands.md`, the release notes and the
  0.8.51 version bump.
- `tests/test_note_commands.py` (renamed from `tests/test_stock_note.py`): the shared cases are
  parametrized over entity/stock/box (save, human line, unchanged, untouched empty note, empty
  refusal, clear, append to empty/non-empty, bare append buffer, `--json`, `--dry-run`, misused
  flags, one commit per call); the kind-specific tests cover a box by name/alias/id prefix, an
  entity by alias/id prefix, ambiguous entity and stock prefixes (including `read_note`), the light
  reader and the three facades. `tests/test_cli_panels.py` pins `note` in the entity and box
  subcommand order.

## Upgrade

Nothing to migrate: no schema, preset, migration step or ledger format changed, and no existing
command changes meaning. `spec_version` stays 7.
